# OnePyProject

An experimental offline project planner for Windows 11 and macOS, built with Python, Qt and pymppwriter. The current source version is **0.2.1**. The editable OnePyProject plan (`.pxplan`) is separate from `MPP` interchange that can also be read and written.

## Run from source

Python 3.10 or newer is required. In the project directory:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[dev]'
python -m onepyproject.app
```

On Windows PowerShell, create the virtual environment with `py -m venv .venv`, then use `.venv\Scripts\Activate.ps1` and run the remaining Python commands. Installers are not yet provided.

The **File** tab contains New, Open, Save, Save As, Import, and Export; the **Project** tab contains task controls, Resources, Assign, and Settings. Toolbar controls show icons only by default; hover for their names or enable **Show toolbar icon names** in Settings. Click **+ Task** to add tasks. Double-click an editable cell (or select it and press F2) to edit it directly; **Edit** opens the full task dialog. Start edits specify an earliest start, so dependencies may move the task later; in the task dialog, set **Start rule** to *Fixed* to hold a task on its date whatever its predecessors say (as Project does for a task that has started), and clear the Start cell to release it. Summary values, finish dates, IDs, and calculated work or duration are read-only. Use **Indent / Outdent** to create summaries. Select multiple tasks using Shift or Command/Ctrl and choose **Link** to create finish-to-start links in row order, or **Unlink** to remove links between the selected tasks. Displayed task IDs follow outline order, including collapsed children. Inserting, deleting or moving tasks updates the displayed IDs and predecessor numbers while keeping links to the same tasks. **Undo / Redo** support up to 100 changes and the usual keyboard shortcuts. **Settings** controls the project start and holidays. **Open** accepts `.pxplan` and MPP14 `.mpp` files; **Import** is an alternative way to open an MPP. MPP opening imports a potentially incomplete copy and recalculates it, leaving the original unchanged. Tasks the file records as started or complete, manually scheduled, or constrained to Must Start/Finish On are held on their file dates; other tasks are driven by their links, with a start-no-earlier-than date only where the file's date is later than the links give. The import reports what it fixed. **Save** saves the working `.pxplan`; **Save As** offers `.pxplan` or `.mpp`. **Export** opens a dialog for MPP, HTML and PDF copies. MPP export shows its warning in the dialog, asks for a template and will not overwrite any existing MPP. Export does not replace saving the working plan.

Choose the destination folder, file name and export type together in the Export window. For MPP, select a user-supplied template in that window; existing MPP files are never overwritten. For HTML or PDF, confirm before replacing an existing file.

Use **Cut**, **Copy** and **Paste** on the Project toolbar or the usual system shortcuts to move or duplicate selected task rows. Selecting a summary includes its descendants. Paste inserts after the selected task and its descendants, at the same outline level; with no selection it appends at the top level. Cut keeps rows in place until they are pasted in the same unchanged project, and the move is one undoable action. Copy can also paste between windows in the same app session. Links between copied rows are remapped; valid outside predecessors are retained within the same project, and unsupported links are omitted. Resources are matched by name or added when needed. The system clipboard also receives tab-separated text for other applications; structured row paste is available during the app session.

Right-click a task row or its Gantt row for cut, copy, paste, edit, delete, link, unlink and new-task actions. Right-clicking an already selected row preserves a multi-row selection. Actions that cannot be used for the current selection are disabled.

The HTML and PDF exports are read-only snapshots of the current plan, including unsaved edits. They contain the task table and a Gantt chart scaled across the full project; predecessors are listed rather than drawn as arrows. Dates omit times by default; select **Show times (HH:MM)** in the export dialog to include them. HTML is one self-contained file with no scripts or external resources and opens offline in a browser. PDF defaults to A4 landscape, with A3 landscape available, and spans pages for long task lists. Both include project data, so share them only with intended recipients. Email providers or organisational policies may still warn about or block attachments. Continue to save a `.pxplan` for editing.

Use **Resources** to add or rename people and teams, set their maximum allocation, and see overallocation warnings. Select a task and choose **Assign** to assign several resources at individual percentages. Alternatively, enter names in the Resource cell, such as `Ada[50%], Ben`; existing resources are suggested as you type, and new names are added to the resource sheet. Select a suggestion with Enter, Tab, or a click; press Enter again to save the cell. Escape dismisses suggestions without choosing one. Resource names containing commas can be quoted, for example `"Ada, Senior[50%]", Ben`. If a name is ambiguous, use **Assign**. Removing a resource requires removing its assignments first. Overallocation warnings do not move tasks. Older `.pxplan` files are migrated when opened; newly saved plans use version 3 and may not open in earlier versions of the application.

Double-click the empty row or empty area beneath tasks, or select it and press **Enter**, to add one. Press **Insert** or **Shift+Enter** on an existing task to add a task above it at the same outline level. With a task selected, **Tab** indents it, **Shift+Tab** outdents it, and **Delete/Backspace** deletes it after confirmation; text-editing keys keep their usual behavior while a cell editor is open. You can turn off task-deletion confirmation in **Settings → User preferences**; deleting a summary also removes its subtasks and their dependency links, and can be undone. Enter task completion as a percentage in the **Complete** column or Task dialog. Summary completion rolls up by child work, falling back to duration for unassigned tasks and a unit weight for milestones. The Gantt draws a dark progress line through task bars. In **Settings → User preferences**, choose which optional task columns to display and enable **Automatically color collapsed summary bars**. Collapsed summaries use a stable 16-color name palette; similar names share related colors, and an explicitly chosen summary color overrides the palette. Expanded summary brackets remain black. Typing a digit on an editable task starts entering its duration in days; this shortcut can be turned off in **Settings** and is remembered for the application. Type a question mark after a duration, such as `2d?`, to mark it estimated; remove the question mark to mark it confirmed. The task dialog also has an estimate checkbox. A summary shows `?` when marked estimated itself or when a descendant is estimated. Milestones and durations of at least one day display dates without times; hover over Start or Finish to see the exact time. Use **− / +** in the bottom bar to change the Gantt timescale up to 100% without changing the schedule. Choose **Comfortable** (default), **Tight**, or **Dense** in **Settings → User preferences** to adjust task and resource row spacing. Previously saved Tight and Dense preferences retain their old spacing under the new Comfortable and Tight names; the old Comfortable setting now uses the new Comfortable spacing.

Choose **System**, **11 Nov HH:MM**, or **YYYY-MM-DD HH:MM** in Settings to change the date display. System uses the operating system's locale. The chosen display format is remembered for the application; date entry remains `YYYY-MM-DD`. Duration, Start, Finish and Work start at content-sized widths and can be resized. **Project-specific settings** contains the current project's name, start, holidays and extra working days. Holidays are not worked; extra working days are worked on the standard hours even on a weekend (for example a catch-up Saturday). Enter a date (`2026-12-25`) or a period (`2026-12-21..2027-01-01`) per line or separated by commas, optionally followed by a name (`2026-12-21..2027-01-01 Christmas shutdown`; names cannot contain commas). Periods must not overlap, and a date cannot be both a holiday and a working day.

Application preferences, including task-column widths, toolbar names, row density, date format, keyboard behavior and zoom, are stored per user with Qt's native settings. The exact location is shown in **Settings**. On macOS it is typically `~/Library/Preferences/com.onepyproject.OnePyProject.plist`; on Windows it is typically `HKEY_CURRENT_USER\Software\OnePyProject\OnePyProject` in the registry. Existing ProjectX preferences are copied once without overwriting new settings or deleting the originals. Project-specific details remain in the `.pxplan` file. The app warns if preferences cannot be saved.

Packaged builds check GitHub for a newer published stable release weekly by default. In **Settings → User preferences**, turn off **Check for updates automatically** or choose a daily, weekly or monthly interval. **Check now** checks immediately. Update checks request release metadata only; no project files or project data are sent. When an update is available, use **View release** to download the matching package. On macOS, open the DMG and drag OnePyProject into Applications; on Windows, quit OnePyProject and replace the extracted app folder. Updates are not installed automatically. Builds are currently unsigned, so macOS Gatekeeper and Windows SmartScreen warnings may appear.

## AI-assisted changes

The **AI** button at the bottom right opens or hides a resizable right-hand assistant. In **AI settings** (gear icon), choose **Azure AI Foundry** or **Gemini Enterprise (Google Cloud)**. For Foundry, enter a public-cloud resource endpoint (for example `https://YOUR-RESOURCE.openai.azure.com/openai/v1/`), deployment name, and API key. Add deployment names in settings or use **Discover models**; verify discovered IDs are deployed. The deployment must support chat completions with structured outputs. The endpoint and deployment names are saved per user. A key is held in memory for the session unless you explicitly choose to remember it in macOS Keychain or Windows Credential Manager; it is never stored in `.pxplan` or regular preferences. If the secure store is unavailable, enter a session-only key. A shared resource key can grant access to other deployments and all users' requests are billed to that resource; protect and rotate it accordingly.

For **Gemini Enterprise**, configure a Google Cloud project ID, location (`global` or a region such as `us-central1`), and a model ID such as `google/gemini-3.5-flash`. Enable Gemini Enterprise Agent Platform/Vertex AI and billing for the project, and grant the signed-in user permission to call Vertex AI. Install the Google Cloud CLI (`gcloud`) and select **Sign in with Google (SSO)** in AI settings; this opens Google's browser sign-in and runs Application Default Credentials login. Your organization's Google identity provider and SSO policies apply. OnePyProject refreshes a short-lived Google access token for each request; it does not save the token or a service-account key in its preferences. The Google Cloud CLI stores ADC credentials locally. Gemini models must support the OpenAI-compatible chat completions API and structured outputs. Model IDs are entered in AI settings; discovery is not available for this provider.

Enter a request and press the **play** button. Type `@` in the prompt to choose a resource from the current resource sheet; use arrow keys and Enter/Tab or click a suggestion. Names containing spaces or punctuation are inserted as quoted mentions. Before the first request to each provider destination and model, approve a data-sharing disclosure; approval is saved in user preferences. Requests send the current project snapshot, including task and resource names, assignments and dates, your request, session conversation and base prompt. Refinements send the staged proposal as the snapshot. The service may charge for requests and may retain or monitor data under its own policies; cancellation can still incur charges. The assistant sends no files and has no tools for running code, accessing files or independently editing the project.

OnePyProject validates proposed operations and calculates the schedule locally. The shield toggles **Ask before applying** (the session default) and **Auto-accept**. Auto-accept applies validated responses as one undoable edit without saving; existing previews still require explicit acceptance or discard. Data-sharing consent, stale-response and validation checks remain in effect. The play button sends; while waiting it becomes a stop button, which cancels locally but may still incur service charges. Choose a reasoning effort beside the model; supported values depend on the deployment, and **default** omits the effort parameter. An unsupported selection produces an error rather than silently changing the setting.

AI-created tasks and tasks whose duration or work it changes are not marked estimated; existing unrelated estimate marks are preserved. In ask mode the main grid and Gantt become read-only during review: green rows are added, red rows removed, yellow rows changed, and darker yellow cells identify changed values. Current Gantt bars are light blue; changed proposed dates appear in darker blue with dashed borders. Scroll to review; change details, including project and resource changes, appear in the dock. Ask follow-up questions to refine the staged proposal, or choose **Accept changes** or **Discard preview**. Acceptance is one undoable working-plan edit and does not save the file. The dock retains the conversation in memory for the session, shows reported token and cached-token counts, and has a clear-session icon. A project change outside the preview clears the conversation on the next request. The editable base prompt is saved in user preferences and follows non-editable safety instructions. Requests are limited to 4,000 characters, 100 operations, 40 conversation entries and a 300 KB project snapshot; larger projects are not silently truncated. The assistant does not automatically level resources or implement unsupported scheduling features. For imported MPPs, review the OnePyProject interpretation carefully because import is lossy.

## Scope and limitations

- The scheduler supports FS, SS, FF and SF links, working-time and elapsed lead/lag, multiple resources per task, fixed-duration, fixed-work or fixed-units tasks, zero-duration milestones and summary rollups. Enter displayed task IDs in the Predecessors cell, for example `5`, `5SS+3d`, `5FF-1d`, `5SF+2d`, `5FS+50%`, or `5FS+2ed`; separate multiple links with commas. FS is the default, and a lag without a unit is treated as working days (`5SF+2` becomes `5SF+2d`). Percentage lag is based on predecessor working duration. Working units are `m`, `h`, `d`, `w`, `mo` (1 day = 8 hours, 1 week = 5 days, 1 month = 20 days); elapsed units are `em`, `eh`, `ed`, `ew`, `emo` (24-hour days, 7-day weeks, 30-day months). Elapsed calculations use local wall-clock time without daylight-saving adjustments. A summary task can be the predecessor of any link type, using its rolled-up dates. A summary can also have FS or SS predecessors, which apply to every subtask beneath it; FF and SF links to a summary are not supported.
- The calendar is Monday–Friday, 08:00–12:00 and 13:00–17:00, with optional holiday periods and extra working days. The week and its hours cannot be changed. No resource levelling or resource-specific calendars are performed. Imported schedules are recalculated and can change. The scheduler has not been verified against Microsoft Project for all dependency combinations, especially finish constraints at non-working boundaries.
- Work is hours, and each allocation is a percentage. Fixed-work duration is work divided by the sum of assigned allocations; at least one resource is required. Fixed-duration tasks calculate work from duration and the sum of allocations. Fixed-units tasks keep their units: edit duration and work is recalculated, or edit work (once a resource is assigned) and duration is recalculated; the schedule itself always uses the stored duration. All resources share the project calendar. Individual calendars, costs, time-varying allocation and automatic levelling are not supported. Overallocation warnings only consider overlapping working time and do not change the schedule. Summary-task assignments may be retained on import but are not scheduled and must be removed before MPP export. This is a simplified model and does not claim full Microsoft Project scheduling equivalence.
- pymppwriter is alpha software. MPP import and export are **lossy** and have not yet been verified in Microsoft Project. Resource names, maximum units, completion percentages and multiple positive-percentage assignments are imported and exported; summary completion is calculated from subtasks and MPP stores whole percentages. Custom summary bar colors are not exported. Fixed-units tasks keep their type through import and export, and zero-percentage assignments are reported and omitted. All four dependency types and working lags can be written; working lags are exported as days. MPP export refuses nonzero elapsed or percentage lags because pymppwriter cannot preserve their units. Import omits nonzero lags whose units the reader cannot safely identify and reports them. Import reads the project calendar's named holiday periods and working days, and reports exceptions with other hours, a different working week, resource calendars and task calendars, which are not applied. MPP export writes the holiday periods but cannot write extra working days that fall on a weekend, so Project will schedule those as non-working; the export reports them. The reader can also omit unscheduled tasks and does not fully read task types. Resource calendars, rates, costs, timephased data, summary-task dependencies, constraints, baselines, custom data and other Project features are not preserved in the OnePyProject model. Import reports some known omissions, not necessarily all losses. Keep the source MPP unchanged and verify exported files in Microsoft Project before relying on them.
- MPP export requires a user-supplied `template.mpp`, which is not included in the repository. OnePyProject removes its resource records before generating a new MPP, but pymppwriter retains other template streams, so exports may still include hidden project data, names, metadata, or other private information. Use a suitably licensed, minimal template and audit exports before distribution. Do not assume that deleting visible tasks removes hidden data.
- The normal Gantt view supports at most 5,000 days of timeline from its start. The AI preview can show a longer combined range, subject to Qt's widget-size limit. Time and dates are local wall-clock values, with no timezone conversions.


## Tests

```bash
python -m pytest
```

The optional integration test uses `template.mpp` if present and writes only to a temporary directory. It checks pymppwriter read-back, **not** Microsoft Project compatibility. Test representative exports in a licensed copy of Microsoft Project, both before and after recalculation.

## Packaging

The **PR checks** workflow runs tests, dependency vulnerability and PR dependency review, and CodeQL. Require the `Tests`, `Dependency audit`, `Dependency review`, and `CodeQL` checks in the `main` ruleset.

The **Protected-tag desktop release** workflow builds macOS Apple Silicon and Windows x64 from a release tag. It verifies that the tag is annotated, points to a commit on `main`, and matches the version in `onepyproject/__init__.py`. It then smoke-tests the packages, creates build-provenance attestations and checksums, and opens a **draft** GitHub Release for review. The update checker uses the latest published stable release and expects `OnePyProject-<version>-macos-arm64.dmg` for macOS and `OnePyProject-<version>-windows-x64.zip` for Windows; draft releases are not offered.

To prepare a release, update the version, merge it through the protected `main` branch, then create and push an annotated tag matching it. For version `0.2.1`:

```bash
git tag -a v0.2.1 -m "Release v0.2.1"
git push origin v0.2.1
```

In GitHub, add a tag ruleset for `v*` that restricts who can create, update or delete release tags. Configure the `release` environment with required reviewer approval; after the workflow creates the draft, review it and publish it manually. Artifacts can be verified with `gh attestation verify <archive> --repo acowls/OnePyProject`.

The **Manual desktop validation builds (not a release)** workflow remains available on `main`; its artifacts expire after seven days. Release packages are not code-signed or notarized, and third-party license compliance is not certified. Review `packaging/THIRD_PARTY_NOTICES.md` and signing/notarization requirements before publishing a draft publicly.
The macOS artifact is a DMG containing `OnePyProject.app`, an Applications shortcut and drag-and-drop instructions. Open the image and drag the app onto Applications. The Windows artifact is a ZIP; extract it fully, then open `OnePyProject/OnePyProject.exe`. Both builds use the OnePyProject application icon. The app is not signed with a developer identity or notarized, so operating-system security warnings are expected. These are **private test builds, not public releases**. No Windows installer is provided.

To build locally in a clean Python 3.12 environment on the target OS and architecture, install `python -m pip install -e '.[dev]' -r packaging/requirements-build.txt`, run `python -m PyInstaller --noconfirm packaging/OnePyProject.spec`, then run `python packaging/package_artifact.py TARGET` with `macos-arm64` or `windows-x64`. The script checks for personal plans and templates, creates the DMG or ZIP, and runs a noninteractive smoke test on the packaged app. The pinned main build dependencies do not constitute a complete reproducible lockfile.

The CI smoke test checks plan saving, the window, SVG icons, HTML and A4/A3 PDF export, but cannot test MPP import/export without a template. To include that local check, set `ONEPYPROJECT_SMOKE_MPP_TEMPLATE` to your external template's absolute path before running `package_artifact.py`; the test writes a disposable MPP in a temporary directory and checks that the template remains unchanged.

The packaging uses separate Qt libraries and includes SVG assets and plugins, but this alone does **not** establish LGPL compliance. Before distribution, review all bundled third-party licences, required notices and corresponding source, library replacement, signing and notarization. See `packaging/THIRD_PARTY_NOTICES.md`; it is not a complete compliance inventory. Keep `template.mpp` external and select it at export time.
