# OnePyProject design decisions

Status: prototype, reviewed 13 November 2026. This document records the agreed direction and the current implementation; it does not claim full Microsoft Project compatibility.

## 1. Goal and boundaries

- Build a free, offline desktop alternative to Microsoft Project for Windows 11 and macOS.
- Use the Microsoft Project Gantt view as the starting point: an editable task grid on the left, a synchronized timeline on the right, hierarchical summary tasks, milestones and dependency lines.
- Support task scheduling by duration or effort and exchange plans in Microsoft Project's binary **MPP14** (`.mpp`) format, used by Project 2010 and later.
- Deliver the basics first. Full scheduling and lossless MPP round trips are goals to investigate, not established capabilities.

## 2. Technology

- **Python 3.10+** for the application, scheduling model and interchange adapter.
- **PySide6 / Qt** for a single cross-platform desktop interface, using a Qt tree grid and custom Gantt drawing. No server or Java runtime is needed by the shipped application.
- **pymppwriter 0.4.3**, pinned to a commit of the `acowls/pymppwriter` fork, for experimental MPP14 reading and writing. It is alpha software and uses a user-supplied MPP template. The fork adds a reader fix (live records only, from long-edited files) and a fix for leads that are not in a PyPI release yet; the pin returns to PyPI once a release has both. The fork reports the same version as PyPI 0.4.3, so the packaging smoke test checks for the fixes and `BUILD_INFO.json` records the source.
- **pytest** for automated tests. **PyInstaller** produces private test builds separately for Windows and macOS. Installers, signing and notarization are not yet validated.
- **Icons8 Flat Color Icons**, using its MIT licence option. SVGs are bundled locally and passed to Qt as scalable icons for high-DPI rendering. Licence and attribution are in `onepyproject/assets/flat_color_icons/LICENSE.txt`.

OnePyProject's own code is licensed under MIT. Its dependencies have separate licences: in particular, PySide6/Qt's open-source licences must be reviewed before distributing a packaged app. Platform signing or notarization may have separate costs.

Alternatives considered: Aspose.Tasks can write MPP but was rejected because it requires a commercial licence. MPXJ is a free MPP reader but cannot write MPP. Microsoft Project XML is a useful interchange fallback, but it is not the binary MPP file the user requested. The Python/pymppwriter stack was selected with the understanding that its alpha status and template-based output require extra verification.

## 3. Application and file architecture

- The application works locally and offline. `onepyproject/model.py` contains the project model and scheduler; `onepyproject/dependencies.py` handles dependency expressions; `onepyproject/resources.py` handles assignments and overallocation; `onepyproject/mpp.py` and `onepyproject/mpp_template.py` handle MPP interchange; `onepyproject/report.py` and `onepyproject/report_pdf.py` produce read-only reports; `onepyproject/app.py` and `onepyproject/resource_ui.py` implement the interface.
- The editable source of truth is a JSON-based **`.pxplan`** file. Current saves use version 2; version 1 files are migrated on load. Version 2 files may not open in older versions of the application. Saves use a temporary file followed by replacement. The `.pxplan` extension and historical `projectx-plan` format identifier are deliberately retained so existing files remain compatible after the rename.
- **Open** accepts `.pxplan` and MPP14. Opening MPP imports an experimental, potentially incomplete copy and recalculates it. The original MPP is not modified. The user is warned before import.
- **Save** saves the `.pxplan` working file. **Save As** can write a `.pxplan` or export an MPP; **Export** opens a file browser with destination, name, type and format-specific options together. The dialog displays the MPP warning and asks for a user-supplied template when that format is selected. Exports do not mark an unsaved working plan as saved. MPP export refuses to overwrite an existing MPP, including the original and template, and publishes a new file from a temporary file.
- HTML and PDF reports are read-only snapshots, including unsaved edits. Both include task details and a Gantt chart scaled to the whole project; dependency expressions are listed, not drawn as arrows. Dates omit times by default, with an option to show them. HTML is a single offline file without scripts or external resources. PDF uses A4 landscape by default, optionally A3 landscape, with repeated headings and pagination. Existing report files require confirmation and report writes are atomic. Reports contain project data and are not substitutes for editable `.pxplan` files.
- MPP14 is the binary Project format, not Project XML. **MSPDI XML is not currently imported or converted by OnePyProject**; pymppwriter does not accept it directly. An adapter could be built later if needed. MPXJ is useful as an independent reader/test oracle but does not write MPP and is not a runtime dependency.

### Template and MPP safety

- Export requires a suitable MPP14 template. The local `template.mpp` is a minimal file (a summary task, a subtask, a task linked after it, and one resource that export removes) and is intentionally excluded from version control.
- OnePyProject removes template resource records and resource-specific calendar records before building an export, using an adapter tied to pymppwriter 0.4.3's internals. This prevents those visible resources from being cloned into the exported resource list; it does **not** prove all hidden template data is removed.
- Other template streams, views, metadata or private data may remain. Use a suitably licensed minimal template and audit files before sharing. Do not overwrite or redistribute a template without checking rights.
- MPP import/export remains lossy and experimental. Keep originals and verify generated files in Microsoft Project. A successfully opened file or a pymppwriter/MPXJ read-back does not prove Project will preserve or recalculate it identically.

## 4. Interface decisions

- Controls are grouped into **File** (New, Open, Save, Save As, Import, Export) and **Project** (Settings, Resources, Assign and task controls) tabs. Project is selected initially. Toolbar buttons show icons without text by default; Settings can enable labels beneath the icons on both tabs, and names remain available as tooltips and accessible labels.
- The leftmost column shows a one-based task number in outline order, followed by task name, duration, start, finish, predecessors, resources, work and mode. Numbers include collapsed descendants and update when tasks are inserted, deleted or reordered; predecessor inputs and labels use these displayed numbers. Stable internal task identifiers and dependency targets remain unchanged, including in existing `.pxplan` files.
- A zero-duration task is shown as a milestone diamond. Summary bars, nested tasks, expand/collapse and dependency lines appear in the Gantt chart. The view can display at most 5,000 days from its timeline origin.
- Zoom **− / +** and its percentage appear in the bottom bar. Zoom changes the Gantt scale, not the schedule, and is capped at 100%. The percentage box is sized for `100%` and does not change width as zoom changes. Controls have explicit contrasting colours and accessible names.
- The bottom bar also offers **Comfortable** (24 px, default), **Tight** (20 px), and **Dense** (18 px) row spacing. Previous Tight and Dense preferences map to Comfortable and Tight to retain their former spacing; previous Comfortable maps to the new, smaller Comfortable. The choice applies to the task grid and resource tables, keeps the Gantt aligned, and is remembered as an application preference without modifying the project.
- Dates use the application preference **System** (default), **11 Nov HH:MM**, or **YYYY-MM-DD HH:MM**. Milestones and tasks of one day or more show dates without times; shorter tasks show times. Tooltips show the full time. Date entry remains `YYYY-MM-DD`. Duration, Start, Finish and Work columns are initially sized for `Duration`, `2020-08-08`, `2020-08-08` and `888 h` respectively; custom task-column widths are saved per user and restored on startup. Expand/collapse arrows are black for contrast.
- Keyboard, toolbar-label, zoom, density, task-column widths and date-display preferences are stored per user using Qt's native settings, not in the project file. The exact location is shown in Settings: typically `~/Library/Preferences/com.onepyproject.OnePyProject.plist` on macOS or `HKEY_CURRENT_USER\Software\OnePyProject\OnePyProject` on Windows. Existing ProjectX settings are copied once without overwriting newer values or deleting the originals. Failed preference writes are reported. Typing a digit on a selected editable task starts editing its duration in days; this shortcut defaults on and can be disabled in Settings. It does not replace text being edited, or edit a calculated summary/fixed-work duration.

### Editing

- Double-click an editable cell or press F2 to edit. **Edit** opens task details. IDs, finish dates, summary calculations and the calculated half of fixed-work/fixed-duration scheduling are read-only. Fixed units allows editing either duration or work (work needs an assigned resource) and recalculates the other. Editing Start specifies an earliest allowed start; a dependency can move it later. The task dialog's **Start rule** can instead *fix* the start: a fixed task stays on its date whatever its predecessors say, shows its Start in bold, and is shown in red with an explanatory tooltip when its predecessors would have started it later. Clearing the Start cell releases a fixed start.
- Double-click an empty row or select it and press Enter to add a task. Insert or Shift+Enter on a task adds one above it at the same outline level; a canceled or empty entry makes no change.
- Tab indents; Shift+Tab outdents. Delete or Backspace removes the selected task after confirmation, including descendants and their links. Normal text-editing keys continue to work in an open editor.
- Select multiple tasks and choose Link for finish-to-start links in row order, or Unlink to remove links between those selected tasks.
- Undo/redo stores up to 100 in-memory changes, with platform-standard keyboard shortcuts. Opening or creating another project resets that history. The saved `.pxplan` determines the clean/dirty state.
- A `?` suffix marks an estimated duration, for example `2d?`; removing it marks the duration confirmed. Task details also expose the flag. A summary displays `?` when marked estimated itself or when a descendant is estimated. Estimates are stored in `.pxplan` and mapped to MPP where supported. AI-created tasks and tasks with AI-generated duration/work are not marked estimated; unrelated existing flags are preserved.

### AI proposal and review

- AI is opt-in and uses a user-supplied Foundry resource endpoint, deployment name and API key. It does not use OAuth, Entra or a hosted agent. The key is session-only unless the user explicitly stores it in the macOS or Windows credential store; regular settings contain no key.
- The user approves a data-sharing disclosure once per endpoint and deployment. Each request sends a bounded current or staged project snapshot, the session conversation and editable base planning prompt. Fixed safety instructions cannot be edited. The model has no filesystem, shell or mutation tools and can only return bounded, versioned operations. Stable task/resource IDs are distinct from displayed task numbers.
- Operations apply to a detached copy and are compared with the original working-plan baseline. The main grid and Gantt show a read-only colored overlay; the dock lists direct and calculated impacts, including project and resource changes. Refinements use the staged candidate, and deleted baseline IDs are reserved. An accepted batch is one undoable edit; a rejected, invalid or stale proposal changes nothing. Save remains explicit.
- Conversation and reported usage are held in memory for the session, while configuration and disclosure approval are per-user preferences. Remote retention, monitoring, location and charges depend on the deployment. Only compatible Foundry v1 chat-completion deployments with structured outputs are supported. Imported MPP limitations and the scheduler's lack of automatic resource levelling still apply.
- The sidebar selects configured deployment names and can query Foundry model IDs, which are not assumed to be deployed. Reasoning effort defaults to the model's default and unsupported values fail visibly. The session-only permission shield defaults to review; auto-accept still validates, rejects stale results and makes one undoable edit without saving. An existing preview always requires explicit acceptance or discard.

## 5. Scheduling model

### Calendar and task dates

- The current project calendar is Monday–Friday, 08:00–12:00 and 13:00–17:00, with configurable whole-day holidays. A working day is 8 hours, week 5 days and month 20 days.
- Leaf-task completion is a validated 0–100 percentage. Summary completion rolls up by child scheduled work, falling back to duration for unassigned tasks and to a unit weight for milestones. Optional task columns and automatic collapsed-summary coloring are user preferences; the 16-color name palette can be overridden on each summary. Custom colors apply only when a summary is collapsed; expanded summary brackets remain black. Gantt task bars show completion as a one-decimal dark progress overlay.
- Schedules use local wall-clock values without timezone or daylight-saving conversions. Elapsed days, weeks and months are 24 hours, 7 days and 30 days respectively.
- **Start rule:** each task has a date (`earliest`) and a rule for it. *No earlier than* (the default) is a floor, like Project's Start No Earlier Than: predecessors can still move the task later. *Fixed* pins the task, like Project's treatment of a task that has started or one with a Must Start On constraint or manual scheduling: its predecessors, and the links inherited from its summaries, never move it, but it still drives its own successors. Links of a fixed task are kept, validated, and still checked for cycles. If its predecessors would start it later, `start_conflicts()` reports it (a warning, not an error). A fixed date before the project start is held at the project start. Summaries have no start rule because they roll up from their children.
- Leaf tasks are recalculated from project start, any entered start date and its rule, predecessors and the supported resource model. Summary start/finish roll up from children, summary work is summed, and summary duration is working time across the rolled-up span.
- There is no automatic resource levelling, configurable working-week editor, individual task/resource calendar, time-varying allocation or resource-cost scheduling. Overallocations warn but do not move tasks.

### Dependencies

- Support **FS, SS, FF and SF**. FS is the default for a bare predecessor ID. Multiple predecessors are supported; cycles, unknown IDs and duplicate predecessors are rejected.
- Accept positive lag and negative lead with working `m`, `h`, `d`, `w`, `mo`; elapsed `em`, `eh`, `ed`, `ew`, `emo`; or `%` of predecessor working duration. Missing lag units default to working days, so `2SF+5` becomes `2SF+5d`.
- A summary task may be the predecessor of any link type and uses its rolled-up start and finish. A link *to* a summary task is limited to FS and SS and acts as a start floor on every leaf beneath it, including leaves of nested summaries, combined with each leaf's own predecessors. A subtask depending on its own summary, or a summary depending on a task that depends on one of its subtasks, is reported as a cycle. FF and SF links to a summary, and external projects, are not supported. FF/SF and working-time-boundary behavior are implemented but still need direct comparison against Microsoft Project.
- MPP export writes supported working-time lags as days. It refuses nonzero elapsed or percentage lags rather than silently change their meaning. Import reads lags in minutes, hours, days, weeks and months as working time and keeps the unit the file shows (Project stores every lag as working tenths of a minute, so the unit only changes how it is displayed; export writes them back as days, which is the same time). Import reports and omits nonzero lags in elapsed or percentage units, which are not working time.

### Resources and effort

- The chosen first resource scope is a shared **Resources** sheet and **Assign** dialog: named people or teams, stable IDs, maximum units, multiple assignments per task and per-assignment percentages.
- The Resource cell also accepts names such as `Ada[50%], Ben`; unknown names are added to the sheet. Inline editing suggests existing resource names case-insensitively, completing the current name without replacing other assignments or their percentages. Names containing commas can be quoted. A referenced resource must be unassigned before deletion. Name ambiguities are resolved through the Assign dialog.
- **Fixed work:** duration = work hours / (8 hours × sum of assignment units). At least one positively allocated resource is required. **Fixed duration:** work = duration in days × 8 hours × sum of assignment units. **Fixed units:** the scheduler uses the stored duration exactly as for fixed duration, and work is derived from it. The difference is in editing: changing the duration recalculates work, and changing the work (which needs an assigned resource) recalculates the duration, keeping the units. Editing assignment units on a fixed-units task keeps the duration and recalculates work; Microsoft Project's behavior there has not been checked. Percentages are converted to fractions for these calculations.
- A resource's maximum units are used for overlap/overallocation warnings, not to cap work or automatically delay tasks. All assigned resources currently share the project calendar and have constant allocation over a task.
- Resource assignments retained on imported summary tasks are not scheduled; MPP export refuses them until removed. OnePyProject also prevents indenting under an assigned task when that would create a new summary with an unscheduled assignment.
- These rules are a simplified subset. Microsoft Project's separate effort-driven behavior, actual work, work contours, resource calendars and costs are not fully modelled.

## 6. MPP mapping and known fidelity risks

- The supported subset maps task hierarchy, dates, durations, estimates, completion percentages, dependency types, working lags, resource names, maximum units and multiple positive-percentage assignments. Fixed-work data is read where it can be represented; exported completion is rounded to a whole percent. Custom summary-bar colors are not mapped to MPP.
- Fixed-units tasks keep their type through import and export, and the import reports nothing for them because the file's work equals duration × units. Exported tasks always write effort-driven off except fixed work. Summary-task links are imported when FS or SS (any type when the summary is the predecessor); FF/SF links to a summary and links to missing tasks are reported and omitted. Each imported leaf gets a start hint chosen in one pass in dependency order (see **Start hints on import**), so the recalculated plan lands on the dates the file stored. Zero-percentage assignments are reported and omitted. Duplicate resource names from MPP are made distinct and reported. Unsupported summary links or unavailable lag units are reported and omitted; not all losses can be detected.
- The reader may skip unscheduled tasks. Resource/task calendars, rates, costs, timephased data, baselines, custom fields, constraints, manual scheduling and other Project-specific information are not comprehensively preserved.
- **Start rules on export:** a fixed task with no progress is written as a Must Start On constraint at its date. A task with progress is written without a constraint, because pymppwriter records its start as the actual start. Floor and link-driven tasks keep pymppwriter's default, which adds a Start No Earlier Than constraint only where the links do not already place the task. pymppwriter's "Project will move it" warning is dropped for fixed tasks, and the export reports once how many fixed tasks start before their predecessors finish; their links are written unchanged. Checked with a real export and re-import of both local samples (import, export through a minimal template, import the exported file): every task keeps its start rule (65-task file 21 fixed, 4 floors, 23 link-driven; 2,367-task file 401, 252, 1,247) and no leaf task's scheduled dates change. The exports carry 1 and 14 Must Start On constraints. Six fixed tasks in the larger file are pinned on a Saturday; the export writes them on the following Monday, which is where the schedule already placed them. The four links with lags in weeks (FS-9w and three FS-2w, milestone to milestone) are imported and exported as days with the same working minutes. Exporting the larger file needs the pymppwriter fix for leads (see section 7). This tests pymppwriter's read-back, not Project's behavior.
- **Project start:** the scheduler never starts a task before the plan start, so the import starts the plan at the earliest task start when that is earlier than the file's recorded project start, and reports the move. In one sample the recorded start was 2026-06-02 while tasks were stored from 2025-11-03; taking the recorded start verbatim recalculated 16 of 65 tasks months later than in the file.
- **Summary links in practice:** in a 2,367-task sample, Project's own stored dates put a zero-lag FS link tight (successor immediately after predecessor) for 92% of leaf-to-leaf links, 78% of leaf-to-summary links, 53% of summary-to-leaf links and 69% of summary-to-summary links, so summary links are honoured. About 20 summary links are not satisfied in the file itself (for example a summary fanning out to four others that Project stored inside its span). Almost all of them belong to tasks Project records as started, which is why started tasks are fixed on import (below).
- **Start hints on import:** the file's stored start is not a single kind of information, so the import chooses a rule per leaf task. (1) A task Project records as started or complete (percent complete above 0), manually scheduled, or constrained to Must Start On / Must Finish On is *fixed* at its stored date, because the file's date is history or an instruction. (2) Every other task is scheduled by its links first. If the links alone reproduce the stored date it gets no hint, so later edits flow through its links; if the stored date is later it gets a *no earlier than* floor; if it is earlier the file breaks its own link, so the task is fixed at the stored date. The pass runs in dependency order so each comparison uses already-placed predecessors, and the import reports how many tasks were fixed for each reason and how many fixed tasks start before their predecessors finish. Measured on the two local samples: the 65-task file has 48 leaves, of which 21 are fixed (20 started, 1 manual), 4 have floors and 23 are link-driven, and every leaf lands on its stored date; the 2,367-task file has 1,900 leaves, of which 401 are fixed (387 started, 14 by their dates), 252 have floors and 1,247 are link-driven, 50 fixed tasks start before their predecessors finish, and 1,892 land on the stored date. The other 8 are stored on dates the Monday–Friday calendar cannot hold (the first is a Saturday; the rest were not examined) and are reported. Before this change every task kept its stored date as a floor, so edits to a predecessor could only push work later.
- **Known import limit:** a stored start time such as 13:00 is reduced to its date. A task Project splits around an unfinished predecessor keeps its start but not necessarily its finish. A started task's stored start is treated as its actual start; this was not checked task by task.

## 7. Verification and next priorities

- The automated pytest suite covers dependency cases, resource calculations, `.pxplan` migration, UI behavior and pymppwriter MPP read-back. Passing tests do not establish Microsoft Project compatibility.
- **Template-based tests and round trips need a populated template.** pymppwriter clones its prototype records from the template, so the template must hold a summary task, a subtask and a task linked after it. Project writes a placeholder assignment row for every task without a resource, so no resource is needed; one that is present is removed by the export adapter. A blank template (no tasks, links or assignments) makes the 17 template-dependent tests fail with "template has no dependency records" or "no assignment records". Those tests skip only when `template.mpp` is absent. With the minimal template in place they all pass.
- **Known pymppwriter 0.4.3 defect with leads:** `link_driven_start` mishandles negative lag. A lead of one day or less is ignored (the successor is placed after the predecessor's finish), and two days or more raises `ValueError: hour must be in 0..23`. One local sample has 9 leads, so exporting it fails with the PyPI 0.4.3. The fix is in the pinned fork commit and is not in a PyPI release yet; with it the sample exports and round-trips.
- An independent MPXJ-based reader has also read sample exported MPP resource and fixed-work fields. It did not recalculate those plans in Microsoft Project. Microsoft Project round-trip/recalculation validation remains outstanding.
- Recommended next work, not yet agreed as implemented scope: preserve imported times, constraints and manual/automatic state; report any conversions that alter a schedule; build representative Microsoft Project-created fixtures and compare after Project recalculates; then expand calendars, fixed-units/effort-driven semantics and other scheduling features based on demonstrated needs.
- Do not treat OnePyProject as a lossless editor or rely on imported/exported schedules for important decisions until the relevant data and calculations have been validated in Microsoft Project.
